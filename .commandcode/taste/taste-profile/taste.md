# Taste Profile
- Prefers acting on an existing established plan over creating new plans or repeating audits; when a plan exists, start implementing immediately instead of re-analyzing. Confidence: 0.9
- Prefers working phase-by-phase with a clear sequence of tasks. Confidence: 0.9
- Before changing a file, understand its existing dependencies and callers; make the smallest safe changes necessary. Confidence: 0.9
- After each major change, run the relevant tests and fix any regression before continuing; keep the application runnable throughout. Confidence: 0.9
- Prefers the agent to actually modify files and implement changes itself rather than stopping to explain what should be done or asking the user to write code manually. Confidence: 0.9
- Preserves existing working functionality; does not want orphaned modules deleted just for cleanup. Confidence: 0.8
- Avoids building speculative/empty future modules or introducing a second/duplicate architecture unless required by a necessary fix. Confidence: 0.8
- When finishing a phase, expects a structured status report covering: files changed, database changes, integration/feature results, what was upgraded, tests passed, live/Windows verification results, and remaining issues. Confidence: 0.95
- Final reports for mockup/spec-driven UI tasks must enumerate exact files changed and explicitly confirm each required aspect: the supplied structure was implemented, existing fields/CRUD/data were preserved, theme round-trip and navigation verified, data isolation intact, test count/result, and that unrelated functionality was left untouched. Confidence: 0.85
- Diagnoses layout/geometry problems by measuring actual widget geometry in the running environment and fixing the root cause (e.g., a footer card inflating and starving the body), rather than applying fragile fixes like fixed heights/grid-propagate hacks that fight the layout manager. Confidence: 0.7
- Prefers edits that add new variables separately and preserve existing variables exactly — do not merge or rename existing column/variable names when introducing a new one. Confidence: 0.8
- Prefers malformed/invalid proposed edits to be rejected and corrected to valid syntax before applying; never apply a malformed edit as-is. Confidence: 0.9
- Prefers a clean, full rewrite of an assignment/line (spelling out the exact variable list and order) over repeated incremental patching of the same line after an edit is rejected. Confidence: 0.9
- During verification/preparation phases, restricts scope: no architectural changes and no speculative code edits; only fix concrete runtime errors actually uncovered during that verification. Confidence: 0.9
- Before handing off for manual verification, verifies the actual runtime environment is ready (target venv interpreter, dependencies installed, all modules import cleanly) and provides the exact launch commands for the user's platform. Confidence: 0.8
- For major product-build phases, perform a complete repository audit first, then produce a written build plan (reuse/refactor/replace analysis, phases, testing and verification strategy), then STOP and wait for explicit user approval before making any code changes. Confidence: 0.9
- Holds a high product-quality bar for the UI: polished, professional, modern desktop look (icon-based sidebar, cards, consistent spacing/typography, light/dark themes, hover/active states, useful empty states, confirmation dialogs) and explicitly rejects demo/prototype aesthetics (giant flat buttons, default-looking Treeviews, placeholder dashboards, personal-finance branding). Confidence: 0.9
- Never ship placeholder buttons or screens that appear functional but do nothing — every UI action must be wired or hidden until implemented. Confidence: 0.9
- Every data-entry/master screen must actually persist to SQLite and every report must read from the real database/services — real functionality over mockups. Confidence: 0.9
- Uses a reference design for visual language/layout quality only, not for copying workflow or domain concepts. Confidence: 0.8
- Expects new functionality to come with tests where practical, not just keeping the existing suite green. Confidence: 0.8
- Requires reusing existing schema and services rather than creating parallel/duplicate versions — explicitly "no duplicate accounting schema"; new masters build on the existing Expenzo tables, and a UI task must never spawn a duplicate service or a second screen for an existing master. Confidence: 0.95
- When the schema evolves, migrations must be additive and idempotent and must preserve existing user data (live DB untouched by upgrades/seeds). Confidence: 0.9
- Demands consistent use of the established UI design system (e.g., Phase 0 Expenzo) and explicitly forbids regressing to older UI designs. Confidence: 0.9
- When master-data screens are introduced, all dependent screens must consume the newly saved master data rather than leaving stale or orphaned data paths. Confidence: 0.8
- Respects the currently selected company context across all views and operations — never hardcodes a default company id (e.g., company_id=1) for new data operations; company isolation must be enforced in queries and validation. Confidence: 0.9
- Requires multi-row database writes (e.g., a voucher header plus its detail lines) to be atomic within a single database transaction so a record can never be partially saved. Confidence: 0.9
- Enforces business rules in the service layer, not just the UI: balanced double-entry (debit = credit), positive/non-zero amounts, accounts must be active and owned by the current company — so validation holds regardless of entry path. Confidence: 0.8
- Prefers soft-cancel over hard-delete for posted financial records: keep the row for audit, mark it Cancelled, and exclude cancelled records from reports immediately. Confidence: 0.7
- Expects automatic sequential numbering for business documents, scoped per company and per document type (e.g., PV-0001, RV-0001, CV-0001, JV-0001). Confidence: 0.7
- Report screens must follow the same professional Expenzo design system as the rest of the app — modern cards, search/filter controls, date filters, account/party selectors, totals/summary sections, empty states, validation/error dialogs, export controls, proper spacing and typography; reports must not look like plain ttk screens. Confidence: 0.8
- UI/UX polish passes must be cosmetic-only and scope-strict: do not modify accounting logic, database schema, voucher or report calculations; do not rebuild architecture, create duplicate services, or add placeholder functionality; keep real data and calculations unchanged and verify (tests + launch checks) that no database/accounting data changed after the pass. Components that are already working correctly (e.g., the theme toggle button/label) must not be touched while fixing a related issue. Confidence: 0.97
- When verifying against a live/real database, uses a temporary test company/data set and cleans up only the temporary test data created (cancel temp vouchers, remove temp export files, drop the temp company), leaving user data intact and the live DB exactly as found. Confidence: 0.8
- New surfaces (e.g., dashboard KPIs) must derive their figures from the same services that power the authoritative reports (Cash Book/Bank Book/Outstanding) so they always agree — never independent re-computation that could drift; tests should assert this cross-agreement explicitly. - Honors explicit phase-scope exclusions strictly: when the user says to exclude a feature (e.g., "exclude Profit & Loss", "do not implement, show, or add a placeholder"), the deliverable must not implement it, list it in menus/navigation, or include even a placeholder card — and verification should assert its absence. - When a verification script writes to a live/real database, its cleanup must run even if a mid-script check fails (try/finally), so a failed run can never leak temp vouchers or files. Confidence: 0.7
- When the console on the Windows target is cp1252 and a symbol cannot be printed, prints only ASCII-safe output (lengths, counts) rather than the symbol itself. Confidence: 0.8
- On the Windows target, verification scripts should avoid printing non-ASCII currency symbols (₹) to the console (cp1252 encoding errors); verify UI label text by content/length rather than printing the symbol. Confidence: 0.6
- Values keyboard-first usability: global shortcuts (Ctrl+S save, Ctrl+N new/clear, Ctrl+F focus the search field, F5 refresh, Alt+F4 exit), logical Tab order on entry forms (Date → Type → Number/Reference → Account → Amount → Narration → Save), Enter must never auto-submit from multiline/text fields, Delete acts only when a record is selected and goes through the existing confirmation, arrow keys navigate focused tables and the sidebar, and entry screens show a visible shortcut/help hint bar so users can learn them. Confidence: 0.95
- Esc must never exit the application — it closes the current popup/dialog first, then returns to the previous screen where appropriate (e.g., Esc from a master sub-screen returns to its hub, exactly as already implemented). Confidence: 0.95
- The main app window should open maximized to the Windows desktop work area on launch (respecting the taskbar, never off-screen or oversized) while keeping standard maximize/minimize/close controls. Confidence: 0.8
- UI/UX polish (keyboard shortcuts, focus/navigation, reskins) must be strictly additive: existing mouse operation, accounting calculations, and database behavior must remain unchanged. Confidence: 0.85
- Prefers a single shared design system (design tokens + theme helper) consumed by every screen; when a screen bypasses it (e.g., uses raw messagebox, default colors, bare ttk look, or a dead control), it is treated as an outlier to be reskinned into the established system rather than tolerated. - State/toggle indicator controls (e.g., the theme button) must display the currently active state — "Light" when Light is active, "Dark" when Dark is active — never the state that will be activated next, and the label must update immediately after every toggle. Confidence: 0.85
- UI text and foreground colors must be theme-aware across the entire app: every screen (dashboard, masters + sub-screens, bank accounts, every report screen, settings) and every widget type (cards, headings, subtitles, labels, tables, buttons, empty states, dialogs) must use the active theme's text/background token pairs rather than hardcoded theme constants, so everything stays clearly readable after switching between light and dark. Confidence: 0.95
- When the theme changes, all existing already-built widgets must re-color immediately in place — the fix belongs in shared theme/color handling (e.g., a palette walker over the widget tree) so the whole app updates without rebuilding screens; verification must cover both directions (Light → Dark → Light) on multiple screens. Confidence: 0.85
- Theme switching must be deterministic and complete after ONE toggle: a single Light→Dark or Dark→Light switch must update every existing widget immediately — never require repeated toggles, delayed refreshes, or screen rebuilds to converge; fix the root cause instead of any multi-step workaround. Confidence: 0.9
- Theme color handling must be based on semantic tokens/roles, not on inferring a widget's meaning from its current hex value (the same hex can represent different tokens across Light/Dark, e.g. #FFFFFF and #0F172A collide); classify each widget's color option by role once, store the identified token, and resolve that token against the active palette. Confidence: 0.9
- Verification of theme switching must assert zero stale colors after EVERY individual toggle — including rapid repeated switching (Light → Dark → Light → Dark → Light) with all screens inspected after each toggle, not just the final end state. Confidence: 0.8
- Active/selected navigation items (e.g., the sidebar item) must be visually distinct with proper contrast in BOTH themes: an accent fill plus a contrasting text/icon color that stays readable in Light and Dark (e.g., dark blue text on a light-blue fill in Light mode), not just the inactive color slightly tinted — and the active state must update immediately both on theme switch and on navigation.
